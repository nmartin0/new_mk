# test_mk7.3 / LITES — distributed design (X series)

The long-horizon work: splitting LITES into servers, and using the distributed
inheritance (DIPC, XMM, NORMA) that this tree uniquely still carries.

Companion to the running list; governed by the same decisions, especially
**D20** (the distributed subsystems stay and are revived), **D24** (byte offsets
are canonical), **D25** (the external pager interface is inviolable) and
**D26** (for IPC, adopt only what adds a field or changes a policy).

*Last updated: 19 September 2026.*

## The X series

Long horizon. Each stage leaves a working system; see the companion document *Beyond LITES: making OSFMK a genuinely distributed system*.

| ID | item | status | notes |
|---|---|---|---|
| X1 | Drivers as rump server tasks | open | Same as K16. Most reliability per unit of work; already on the roadmap. |
| X2 | Restart server | open | MINIX's `rs` in Mach form: hold each server's binary, arguments and startup ports; request dead-name notifications on its task port; relaunch on death. Cheap once X1 exists, and it makes a driver crash non-fatal. |
| X3 | Network out to its own server | open | The moment the system stops being single-server: the emulator makes its first routing decision, socket fds to one server, file fds to another. |
| X4 | The fd table moves into the emulator | open | Descriptors become an array of **ports**. `dup`, `close`, close-on-exec become local, RPC-free. The largest single change and the one that makes everything after it cheap. |
| X5 | Per-filesystem servers | open | LITES keeps namespace resolution at first; each server owns its own inodes and locks. |
| X6 | Client-side path resolution | open | Directory ports plus per-component lookup, mount points returning a port to the next server (Hurd translators, QNX prefixes). The central VFS disappears. Point of no return. |
| X7 | Split proc, pipes and tty out | open | What remains of LITES becomes the proc server; pipes/FIFOs/unix sockets and the tty layer become their own servers. |
| X9 | Build the routing layer as a standalone library (`libposix_client`) | open | fd table as an array of ports, server lookup, signal-frame construction. Used by the emulator first, linked into libc later — the same code either way, which is what makes the transition gradual instead of a flag day. **Hard constraint: it must be rtld-safe** — no malloc, no libc dependency, no global constructors, bootstrapping its own ports from the task's bootstrap port — because the dynamic linker needs `openat`/`mmap`/`mprotect` before libc is initialised. Design for that from the first line (Q11). |
| X10 | Follow LITES's `emulator/libsyscall` model for the bypass | open | The authors sketched exactly this seam and never filled it in: the directory holds `libsys.h` and `libsys_support.c`, whose entire content is `int errno = 0;`. Adopt the shape — libc calling the routing library directly instead of trapping — and finish it. |
| X11 | Server-side semantics: rump first, a **thin** helper library second | open | **Revised.** Both QNX (`iofunc_*`) and the Hurd (`libports`, `libfshelp`, `libiohelp`, `libdiskfs`, `libnetfs`, `libtrivfs`, `libpager`) converged on a shared server-side library, which is evidence the shape is forced — but both are also large, and a fat shared library becomes a second kernel that every server links and nobody can change. **Where servers are rump kernels, NetBSD's vnode layer already provides POSIX object semantics**, tested, so no helper is needed for filesystems at all. Keep a thin library only for what rump does not cover — pipes, ttys, sockets as standalone servers. Keep the protocol narrow (Plan 9's 9P is the minimal-protocol counter-model). The conformance suite (U8), not the library, is what actually prevents divergence. |
| X12 | Signal delivery without a signal thread | open | **Revised — the Hurd's per-process signal thread is the wrong model here.** XNU never builds a frame from outside: `psignal` marks the thread and calls `act_set_astbsd`, and the thread delivers its own signal at its next return to user mode, where its state is clean by definition. In an RPC world the **reply message is that boundary**, so: (1) **synchronous signals** (SIGSEGV/BUS/FPE/ILL) arrive as Mach exception messages with the thread already stopped — use `exception_raise_state_identity` (present in 7.3's `mach/exc.defs`) to return the modified register state in the reply, and the thread resumes directly in the handler: one round trip, no suspension, no race; (2) **async signals to a thread inside an RPC** ride back on the reply it is already waiting for, and the client stub builds the frame — XNU's AST exactly, at no cost; (3) **async signals to a thread spinning in user code** are the only heavyweight case, and the server drives it with `thread_abort_safely` + `thread_get_state` + `vm_write` + `thread_set_state`, with a shared per-thread flag page (extended `MAP_UAREA`) for cheap checks at cancellation points. No extra thread per process. |
| X13 | Generate RPC stubs from NetBSD's own syscall lists | open | NetBSD builds libc's stubs from `lib/libc/sys/Makefile.inc` (410 lines); only 44 `.c` and 13 i386 `.S` files are hand-written. Replace the generator, keep the input list, and the stub layer tracks upstream instead of forking it. |
| X14 | Port context word (badge) — **implementation planned** | open | **Why:** a server receiving on a *port set* is told which set the message came from, not which port, which is why LITES calls `port_object_hash_lookup()` on every message. Delivering the port's own context removes that lookup from every RPC in the system. **Design: a new trailer element**, following the precedent already in the tree — `mach_msg_security_trailer_t` (`mach/message.h:552`) delivers `msgh_seqno` and `msgh_sender` exactly this way, and the receiver selects how much it wants with `MACH_RCV_TRAILER_ELEMENTS()`. Rejected alternative: GNU Mach's protected payload, which replaces `msgh_local_port` in the header — faster, but it changes semantics MIG-generated code relies on, and GNU Mach is GPL (design reference only). **Changes:** (1) `ipc/ipc_port.h:204` add `ip_context` to `struct ipc_port`, zeroed in `ipc_port_init` (`ipc_port.c:659`); (2) `mach/message.h` add `mach_msg_context_trailer_t` with `msgh_context` after `msgh_sender`, make it the widest FORMAT_0 variant, add `MACH_RCV_TRAILER_CONTEXT 3` beside the existing NULL/SEQNO/SENDER at line 719 — `MAX_TRAILER_SIZE` then follows from the struct; (3) `ipc/mach_msg.c:224` add the size to the `trailer_size[]` table; (4) `ipc/mach_msg.c:428` and `:1550`, the two receive sites that set `msgh_trailer_size` from `REQUESTED_TRAILER_SIZE(option)`, copy `ip_context` **from the port the message actually arrived on**; (5) `mach/mach_port.defs` add `mach_port_set_context` / `mach_port_get_context`, implemented in `ipc/mach_port.c`, **requiring the receive right** so a client cannot forge a badge. **Semantics:** context belongs to the port, travels with the receive right, zero on creation. **Compatibility:** nothing requests the new element, so existing code is unaffected. **Prerequisite:** new `.defs` routines mean regenerating MIG stubs — lands after R9/R20. **Risk to measure (Q12):** `MAX_TRAILER_SIZE` feeds `msg_and_trailer_size = size + MAX_TRAILER_SIZE` (`ipc_kmsg.c:793`), which interacts with `IKM_SAVED_KMSG_SIZE` (256 bytes) — growing the trailer shifts the boundary where a message stops fitting the cached buffer, which cuts against the optimisation. **Consumer:** a few lines in LITES's `ux_server_loop`, swapping the hash lookup for a trailer read. **Size:** ~6 files, ~150 lines, one deviation. **Test:** set a context, receive on a port set, confirm the right value arrives; then the null-RPC benchmark with and without (X19). |
| X21 | Study **Mach-US** — CMU's multiserver UNIX, which is this design already built | open | `nmartin0/mach_us`, `VERSION = US53`, tested on MK83, from CMU-Mach and OSF-RI (Julin, Stevenson and others). Its own description: separate servers for file systems, network, process management and tty, plus "an emulation library loaded into each user process… **There is no 'central' server**… **All multi-service actions are controlled by the emulation library**" — which is X4, X6 and X9, shipped in 1994. Contents: servers `ufs` 8,694 lines, `net` 123,263 (Arizona x-kernel TCP/IP), `tty` 6,918, `tm` 4,796 (process manager), `as` 8,951 (address space), `pipenet` 6,106, `name`, `config`, `diag`; libraries `us++` 31,397 (object interfaces), `emul` 14,078, `ux` 8,500, `mach3`, `threads`, `proxies`; tools `us_ps`, `fsadmin`, `machid`. **Read `doc/` first** — the 1991 Usenix Mach Symposium paper, `us_analyze`, `naming-0891`, `fs_fork_tcp_tour`, `overview-0791` — they are the design rationale for the questions X6 and X11 are still open on. |
| X26 | Read XNU's replacements for the subsystems this design reworks | open | Same job, rewritten, with 7.3 as the common ancestor (G117): `wait_queue.c` → **`waitq.c` 2,678** (wait-queue *sets* with prepost — exactly what L35 needs); `sync_lock.c` 934 → **`turnstile.c` 3,708** (priority inheritance for locks *and* IPC — the inversion problem X8/X15 circle without solving); `lock.c` 2,085 → `locks.c` 3,328; `mk_sp.c` → `sched_clutch.c` 6,017; `thread_swap.c` → **`vm_compressor.c` 6,583** (compressed memory on the same memory-object interface — relevant to L27 and the default pager); `ledger.c` 445 → **2,899**, the same file 6.5× larger, being the machinery X17's session quotas build on; and **`ipc_importance.c` 3,906**, which has no 7.3 ancestor at all — importance donated across message boundaries, the scheduling analogue of X17's ledgers. Design references under D21. |
| X20 | Read FLIPC's communications-buffer design before building any fast path | open | The tree already contains a user-level shared-ring messaging layer (K12, G61), written by people solving this exact problem, permissively licensed, i386-ported. Its user-side/kernel-side split mirrors the routing-library/kernel split in X9. Extract the design — ring layout, wired-buffer management, the rule that no CB structure is user-visible and the interface layer mediates all access — before designing X15's small-message path. |
| X15 | IPC fast paths: handoff on call, small-message path, traps for kernel objects | open | (a) **Handoff**: a send-then-wait should switch directly to the receiver carrying the sender's time slice, L4's central trick; 7.3 has `thread_switch` handoff and `lock_handoff` but not on the `mach_msg` RPC path. (b) **Small-message path**: no buffer allocation for short fixed messages, per-thread cached buffer. (c) Semaphore ops as traps (K2/K3). (d) Commpage and per-thread shared flag pages so hot reads need no RPC at all. (e) Protocol discipline: map bulk data rather than copying, batch (`readdir` returns many entries). **Measure first — build a null-RPC benchmark into R16 before optimising anything.** |
| X19 | Null-RPC benchmark — **and `net-latency-tools` for the network side** (G154): Chris Maeda, CMU 1993, **public domain**, `client.c` 478 lines + `tcp_server.c` + `udp_server.c`, measuring TCP/UDP round-trip latency. Usable as-is. Null-RPC benchmark in the test harness | open | **The first X-series deliverable, and it gates the rest.** Every performance claim in this design — handoff, badges, small-message paths, migrating RPC — is a plausible story without a number. Measure: null RPC round-trip (no arguments, no rights), the same with a 4 KB in-line payload, the same with out-of-line memory, port-set receive versus single-port receive, and the same call with and without the hash lookup. Runs as a Mach-level test under R16, so it needs no LITES, no libc and no shell. Record results in `docs/` so regressions are visible; re-run after each of X14 and X15. **Part 1 done 22 Sep (G194):** `ipc/ipc_bench.c` in the K46 unit tests measures null RPC, 4 KB in-line, and port-set receive through `mach_msg_overwrite()` -- the real IPC core, less the trap and user copies. Results in `notes/docs/ipc-baseline.md`: under TCG, 10,352 / 21,804 / 9,794 TSC ticks per round trip (spread 4-15%); 4 KB in-line costs 2.1x a null RPC, a port set no more than a port. Still ahead: out-of-line memory, the hash lookup, KVM figures, `net-latency-tools`. |
| X22 | Revive NORMA: build it, boot it, keep it in CI | open | **Donor identified (G171): OSFMK 6.1's `norma/` — 65 files / 43,174 lines in one directory, a strict superset of CMU MK84's and the direct ancestor of what 7.3 kept.** 7.3 *kept* the 16 `xmm*`/`svm_*`/`vm_copy` files, *dropped* the whole CMU `ipc_*` transport plus six XMM layers, and *replaced* the transport with 15 `dipc_*` files — so **DIPC is a rewrite of NORMA's IPC half while the XMM half survived**. 6.1 is the port source: it already carries the `svm_*` files 7.3 expects, its `ipc_ether.c` is 1,389 lines against CMU's 1,113, and it adds `ipc_lazy.c`/`norma_lazy.c` (lazy evaluation of norma operations) and `tr.c` (tracing) that CMU lacks. Drift 6.1→7.3 on surviving files is moderate (`xmm.c` 254 diff lines, `xmm_object.c` 247, `vm_copy.c` 385). **CMU's MK84 (G170) is the pre-OSF reference only.** It has **`ipc_ether.c` (1,113 lines), a complete Ethernet transport** where we have only KKT — directly relevant to the transport decision below — and **six XMM layers we lack**: `xmm_buffer.c` 666, `xmm_invalid.c` 328, `xmm_shadow.c` 275 (distributed shadow objects), `xmm_copy.c` 261, `xmm_interpose.c` 251 (the layer-stacking mechanism), `xmm_debug.c`. Ours has seven it lacks (the `svm_*` coherence files). Complementary, not redundant. | Q15 first. Then: a `FAST+NORMA` configuration in the boot test (R4) so the distributed code cannot silently rot; resolve the `FAST_IDLE` contradiction between `config.norma` and `config.mp`; and decide the transport — `i386/kkt` (`kkt.c`, `if_kkt.c`) over an Ethernet interface, which depends on K24's NIC fix landing first. |
| X25 | Read the netmsgserver — distributed IPC as a **server**, over TCP | open | `RhapsodiOS/src/nmserver-1`, 103 files / 25,192 lines (G106): transparent cross-node ports in **user space over ordinary TCP**, with `netname` name service, port bookkeeping across nodes (`portops.c`, `portrec.c`, `portsearch.c`), transport (`tcp.c`, `datagram.c`, `transport.c`), **`ipc_swap.c`** for byte-order translation between heterogeneous machines, and **authentication and access control** (`crypt.c`, `km_server.c`, `km_procs.c`, `ps_auth.c`, `access_list.c`, `multperm.c`). **This is the other historical answer to X22–X24, and it composes with section K far better than NORMA does** — it is a server, over a normal network, where NORMA is in-kernel over KKT. It also addresses X23's cross-node identity gap directly, which NORMA does not. APSL 1.1 with the §7 election to 2.0 (G103); read first, and consider whether the design supersedes the NORMA revival or complements it. |
| X23 | The distributed gaps NORMA does not fill | open | NORMA supplies the hard parts — cross-node IPC and distributed shared memory. Missing for a complete cluster: **membership and quorum**, **failure detection** beyond dead-name notifications, **cross-node identity** (K5's audit trailer is node-local, so identity stops at the node boundary — this is the deepest of the four), **time synchronisation**, and **a cluster filesystem** (`NORMA_SCSI` is shared-disk access, not a coherent distributed FS). Each is a design item, not an import: Tru64's TruCluster CFS was never released, and AdvFS — the part HP did release, in 2008 — is **GPL-2.0-only**, is the *local* filesystem rather than the distributed one, and was written against the OSF/1 monolithic VFS rather than Mach interfaces (G96). |
| X24 | Distributed filesystem the Mach way — **and `xmm_interpose.c` (G170) shows how XMM layers compose**, which is the mechanism a distributed filesystem's coherence would be built from. Distributed filesystem the Mach way, not the cluster-FS way | open | Once X5 gives per-filesystem servers and X6 gives client-side path resolution, a filesystem server reached through a port becomes **distributed for free** when DIPC carries that port across nodes and XMM keeps its pages coherent. The design work is in the failure semantics (X16) and cross-node identity (X23), not in the filesystem. This is the payoff that justifies keeping the NORMA inheritance (D20). **Protocol: 9P is the fit** (G118) — MIT since 2021, thirteen operations, no notion of where the server lives; `libixp` is under 2,000 lines and POSIX-portable. **Boundary mechanism: NetBSD's `sys/coda`** — 5,579 lines of C under CMU's permissive Coda notice, a VFS module forwarding operations to a userspace process, portable to LITES's 4.4BSD VFS with any server behind it. Not Coda itself (GPL-2, C++, and it cannot be a root filesystem), and not a 1990s cluster FS. **NFS is already in LITES** (`nfs/`, 21 files / 13,607 lines) as the non-coherent baseline. |
| X16 | Define failure semantics when a server dies mid-call | open | The gap in the first draft of this design. A client blocked in an RPC to a dead server needs a defined outcome (dead-name notification → error → re-open in the routing library), and a restarted server must be safe to talk to again, which means operations are idempotent or transactional. QNX and Genode define this carefully; MINIX gets away with less because its drivers are stateless. Design, do not assume. |
| X17 | Session quotas on top of 7.3's hierarchical ledgers | open | **Most of the machinery already exists**: `ledger_create(parent, ledger_ledger, out new_ledger, transfer)` makes a child ledger and *moves* resource into it; `ledger_transfer(parent, child, transfer)` moves more; `task_create(target_task, ledger_ports, inherit_memory, out child)` creates a task against ledgers (G57). Genode's donation model, in the kernel, from 1998. A client opening a session creates a child ledger, transfers a quota in, and passes the port in the open RPC; a greedy client exhausts its own budget and the server is untouched. **One kernel change needed**: VM allocation must accept a ledger to charge, since today charging is at task granularity. |
| X18 | Parent-mediated service lookup, global filesystem namespace | open | Already in Mach: every task has a **bootstrap port** chosen by its creator (`task_get_bootstrap_port` — how the emulator finds LITES today, `emul_init.c:62`). Service lookup goes through it; path resolution goes through a separate **root directory port**. Keeping the two separate gives containers for free — a different root port is `chroot` with no way to escape upward, a restricted bootstrap port is a restricted service set — with no new kernel concepts and no policy in Mach. |
| X8 | Answer Q5 "keep it" if going distributed | open | Migrating-thread RPC (`mach_rpc_trap`, `thread_act`, `thread_pool`, `rpc.c`) is designed for exactly the chained cross-server call a multiserver system makes constantly. XNU dropped it, GNU Mach never had it — it is this kernel's distinctive asset in this design. |
